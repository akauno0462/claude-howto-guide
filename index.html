01 · Slash Commands

Slash Commands 参考指南

Claude Code 的快捷命令系统——输入 / 即可调用

概览

Slash command 是在 Claude 交互式会话中控制行为的快捷方式，分为几类：

  • 内置命令：Claude Code 自带，例如 /help、/clear、/model
  • Skills：用户自定义命令，基于 SKILL.md 文件，例如 /optimize、/pr
  • 插件命令：来自已安装插件的命令，例如 /frontend-design:frontend-design
  • MCP prompts：来自 MCP server 的命令，例如 /mcp__github__list_prs
注意：自定义 slash command 已经合并进 Skills。.claude/commands/ 仍然可用，但现在更推荐使用 .claude/skills/。两者都会创建 /command-name 形式的快捷命令。

01 · Slash Commands

自定义命令

通过 Skills 创建自己的快捷命令

把自定义命令做成 Skill

创建一个包含 SKILL.md 的目录：

mkdir -p .claude/skills/my-command

文件：.claude/skills/my-command/SKILL.md

---
name: my-command
description: 这个命令的作用，以及何时使用它
---

# 我的命令

当该命令被触发时，Claude 需要遵循的说明。

1. 第一步
2. 第二步
3. 第三步

Frontmatter 参考

字段作用默认值
name命令名（会变成 /name）目录名
description简短说明第一段
argument-hint自动补全时的参数提示无
allowed-tools命令可无权限使用的工具继承
model指定模型继承
disable-model-invocation若为 true，只有用户能调用false
user-invocable若为 false，不会出现在 / 菜单中true
context设为 fork 时在隔离 subagent 中运行无
agentcontext: fork 时使用的 agent 类型general-purpose
hooksSkill 范围内的 hooks无

参数替换

使用 $ARGUMENTS 接收全部参数：

---
name: fix-issue
description: 根据编号修复 GitHub issue
---
按团队编码规范修复 #$ARGUMENTS

调用 /fix-issue 123 时，$ARGUMENTS 会变成 123。

使用 $0、$1 等接收单个参数：

---
name: review-pr
description: 按优先级审查 PR
---
审查 #$0，优先级为 $1

调用 /review-pr 456 high 时，$0="456"，$1="high"。

Shell 命令注入动态上下文

在 prompt 发送前，可用 !`command` 先执行 shell 命令：

---
name: commit
description: 使用上下文创建 git commit
allowed-tools: Bash(git *)
---
## 上下文
- 当前 git 状态：!`git status`
- 当前 diff：!`git diff HEAD`
- 当前分支：!`git branch --show-current`
- 最近提交：!`git log --oneline -5`

MCP Prompts 作为命令

MCP servers 可以把 prompt 暴露成 slash command：

/mcp__<server-name>__<prompt-name> [arguments]

/mcp__github__list_prs
/mcp__github__pr_review 456
/mcp__jira__create_issue "Bug title" high
01 · Slash Commands

安装与最佳实践

作为 Skills（推荐）

# 创建 skills 目录
mkdir -p .claude/skills

# 对每个命令文件，创建一个 skill 目录
for cmd in optimize pr commit; do
  mkdir -p .claude/skills/$cmd
  cp 01-slash-commands/$cmd.md .claude/skills/$cmd/SKILL.md
done

作为旧式命令

# 项目范围（团队）
mkdir -p .claude/commands
cp 01-slash-commands/*.md .claude/commands/

# 个人使用
mkdir -p ~/.claude/commands
cp 01-slash-commands/*.md ~/.claude/commands/

最佳实践

应该做不要做
使用清晰、以动作导向的命名为一次性任务创建命令
在 description 中写清触发条件在命令里写太复杂的逻辑
保持命令聚焦于单一任务硬编码敏感信息
有副作用时使用 disable-model-invocation跳过 description 字段
用 ! 前缀注入动态上下文假设 Claude 知道当前状态
把相关文件组织进 skill 目录所有内容都塞进一个文件

故障排查

找不到命令：

  • 检查文件是否位于 .claude/skills/<name>/SKILL.md 或 .claude/commands/<name>.md
  • 确认 frontmatter 中的 name 与预期命令名一致
  • 重启 Claude Code 会话
  • 运行 /help 查看可用命令

Skill 与 Command 冲突：如果同名同时存在，skill 优先。删除其中一个或重命名即可。

02 · Memory

Memory 指南

让 Claude Code 跨会话保留项目规范、规则和个人偏好

概览

Memory 让 Claude Code 在不同会话之间保留上下文。把团队规范、项目规则、个人偏好和目录级约束写进 CLAUDE.md，Claude 会在合适时自动加载。

Memory 命令速查

命令作用
/init初始化项目级 CLAUDE.md
/memory打开并编辑记忆文件
#快速把当前规则写入 memory

快速上手

使用 /init

在项目目录中运行 /init，Claude 会根据当前项目生成一个 CLAUDE.md。

使用 # 快速更新记忆

# 这个项目始终使用 TypeScript 严格模式
# 优先使用 async/await，而不是 promise 链
# 每次提交前都运行 npm test
# 文件名统一使用 kebab-case

Memory 架构

层级作用范围典型内容
受管策略组织级合规、安全、统一流程
项目记忆单个项目架构、编码标准、工作流
目录记忆子目录模块约束、局部规范
用户记忆单个用户个人偏好、默认设置

目录结构示例

project/
├── CLAUDE.md
├── src/
│   ├── CLAUDE.md
│   └── api/
│       └── CLAUDE.md

Auto Memory

Auto memory 让 Claude 根据当前目录自动寻找并加载合适的记忆文件。Claude 会根据当前工作目录、父目录和已配置路径，逐层查找相关 memory。

最佳实践

应该做的：用项目记忆保存团队标准，用目录记忆保存局部差异，先写简洁规则再逐步补充，把可重复内容写进 CLAUDE.md。

03 · Skills

Agent Skills 指南

可复用、可自动触发的能力包

概览

Skills 是可以复用、可自动触发的能力包。一个 skill 通常包含 SKILL.md、参考文件、脚本和模板。Claude 在合适的场景下会自动加载它。

主要好处：可复用、可渐进加载、可以把脚本/模板/说明放在一起、适合标准化流程

渐进式披露（三层加载）

  1. 只看描述：先判断这个 skill 是否相关
  2. 加载 SKILL.md：读取核心说明
  3. 按需加载支持文件：脚本、模板、参考资料

Skill 目录结构

my-skill/
└── SKILL.md

# 复杂的 skill 结构
code-review/
├── SKILL.md
├── scripts/
│   ├── analyze-metrics.py
│   └── compare-complexity.py
└── templates/
    ├── review-checklist.md
    └── finding-template.md

SKILL.md 格式

---
name: my-skill
description: 这个 skill 的用途，以及什么时候触发
---

# Your Skill Name

## Instructions

## Examples

可选 frontmatter 字段

字段说明
argument-hint自动补全提示
allowed-tools工具白名单
model模型覆盖
disable-model-invocation禁止 Claude 自动调用
user-invocable是否出现在 / 菜单
context执行上下文（fork 等）
agentsubagent 类型
hooksskill 内 hooks

控制调用方式

通过 disable-model-invocation、user-invocable 和工具白名单来控制 Claude 是否能自动调用 skill。

动态上下文注入

- 当前 git 状态：!`git status`
- 当前 diff：!`git diff HEAD`
- 当前分支：!`git branch --show-current`
03 · Skills

高级与最佳实践

Skills vs 其他功能

功能触发方式适合场景
Skills自动/半自动复用能力、流程标准化
Slash Commands手动快捷命令
Subagents自动委派隔离任务
Hooks事件触发自动化和验证

最佳实践

  1. 描述要具体——让 description 明确说明触发条件
  2. 保持聚焦——一个 skill 解决一个问题
  3. 包含触发词——在描述里加入相关关键词
  4. SKILL.md 不要太长——尽量控制在 500 行以内
  5. 引用支持文件——把重复内容移到脚本或参考文件中

安全注意事项

  • 不要在 skill 中硬编码密钥
  • 对副作用操作保持用户触发
  • 给自动触发的 skill 设置清晰边界

故障排查

Skill 没有触发：检查描述是否足够具体、目录是否在 Claude 可见范围内、是否被更高优先级的 skill 覆盖

Skill 触发太频繁：收紧描述、增加约束条件、用更具体的触发词

04 · Subagents

高级用法

串联 Subagents

复杂任务里可以让多个 subagent 依次协作：

  1. 代码审查
  2. 测试生成
  3. 文档更新

后台 Subagents

有些 subagent 可以作为后台任务执行，不阻塞主会话。

Worktree 隔离

可以为 subagent 分配独立的 worktree，不同任务就不会互相污染文件状态。

Agent Teams（实验性）

Agent teams 是更高级的协作模式，适合多个 subagent 并行处理复杂任务。

SubagentsAgent Teams
侧重委派单个任务多角色协作
适用独立任务大型流程

最佳实践

  • 设计原则：单一职责、描述明确、工具权限最小化
  • System Prompt：任务说明要具体、不要写太长、只保留执行任务所需的信息
  • 工具访问策略：审查型 subagent 只读、实现型适度开放写权限、高风险动作保持审批

什么时候使用 Subagents

  • 任务可拆分
  • 需要隔离上下文
  • 需要明确角色分工
  • 需要并行协作
05 · MCP

MCP (Model Context Protocol)

Claude Code 访问外部工具、服务和 API 的标准协议

概览

MCP 是 Claude Code 访问外部工具的协议。你可以把 GitHub、数据库、文件系统等都接到 Claude 里。

MCP 架构

MCP 通常由三部分构成：Claude Code → MCP server → 外部工具或数据源

传输方式

方式推荐度说明
HTTP 传输推荐标准 Web API 方式
Stdio 传输本地本地 Node.js/Python server
WebSocket实时需要实时双向通信的场景

设置流程

  1. 确认要接入的服务
  2. 选择 transport
  3. 配置环境变量或认证
  4. 在 Claude Code 中添加 server
  5. 验证工具是否可用

MCP 配置管理

# Add HTTP-based server
claude mcp add github -- npx -y @modelcontextprotocol/server-github

# List all MCP servers
claude mcp list

# Remove an MCP server
claude mcp remove github

把 MCP Prompts 暴露成 Slash Commands

/mcp__<server-name>__<prompt-name> [arguments]

/mcp__github__list_prs
/mcp__github__pr_review 456
/mcp__jira__create_issue "Bug title" high

作用域

  • 项目级：.mcp.json（团队共享）
  • 用户级：~/.claude.json（个人）

安全注意事项

应该做：只授权必要的工具、优先使用最小权限、检查输出是否可信
不要做：不要把高风险 token 写死在仓库里、不要默认开放所有工具、不要忽视网络和认证风险

故障排查

  • 找不到 MCP Server：检查是否安装、路径和配置是否正确
  • 认证失败：检查环境变量是否设置、确认 token 权限正确
  • 连接超时：检查网络和 server 是否可用
06 · Hooks

Hooks 参考

事件驱动的自动化机制

概览

Hooks 是在 Claude Code 事件发生时自动执行的 shell 命令，用于格式化、校验、通知、审计等自动化工作。

常见用途：写文件前自动格式化、提交前运行测试、扫描安全问题、记录 bash 命令、校验用户提示词、发送团队通知

Hook 类型（4 类，25 个事件）

类别事件
Tool HooksPreToolUse, PostToolUse, PostToolUseFailure, PermissionRequest
Session HooksSessionStart, SessionEnd, Stop, StopFailure, SubagentStart, SubagentStop
Task HooksUserPromptSubmit, TaskCompleted, TaskCreated, TeammateIdle
Lifecycle HooksConfigChange, CwdChanged, FileChanged, PreCompact, PostCompact, WorktreeCreate, WorktreeRemove, Notification, InstructionsLoaded, Elicitation, ElicitationResult

安装方式

mkdir -p ~/.claude/hooks
cp 06-hooks/*.sh ~/.claude/hooks/
chmod +x ~/.claude/hooks/*.sh

配置

在 ~/.claude/settings.json 里配置：

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Write",
      "hooks": ["~/.claude/hooks/format-code.sh"]
    }],
    "PostToolUse": [{
      "matcher": "Write",
      "hooks": ["~/.claude/hooks/security-scan.sh"]
    }]
  }
}

最佳实践

  • 把 hooks 保持短小明确
  • 只做单一职责
  • 先在本地测试
  • 不要在 hook 里放复杂业务逻辑
  • 对副作用保持谨慎

故障排查

  • 检查文件路径和权限
  • 确认脚本可执行
  • 检查 settings.json 语法

08 · Checkpoints

Checkpoints 与 Rewind

保存对话状态，安全地探索多种方案

概览

Checkpoints 会保存会话状态，让你可以安全地试验和探索多种方案。它们本质上是当前对话状态的快照，包含：所有已交换的消息、已做出的文件修改、工具使用历史、当前会话上下文。

核心概念

概念说明
Checkpoint保存消息、文件和上下文的对话快照
Rewind回到之前的 checkpoint，并丢弃之后的更改
Branch Point从同一个 checkpoint 出发，探索多个方案

访问方式

快捷键：按两次 Esc（Esc + Esc）

命令：/rewind（别名：/checkpoint、/undo）

Rewind 选项

  1. 恢复代码和对话 - 把文件和消息都恢复到那个 checkpoint
  2. 恢复对话 - 只回退消息，保留当前代码不变
  3. 恢复代码 - 只回退文件修改，保留完整对话历史
  4. 从这里开始总结 - 压缩对话成 AI 摘要
  5. 算了 - 取消并返回当前状态

自动 Checkpoints

  • 每次用户输入都会自动创建 checkpoint
  • Checkpoints 会跨会话保留
  • 30 天后自动清理旧 checkpoints

使用场景

场景工作流
探索不同方案保存 → 试方案 A → Rewind → 试方案 B → 比较
安全重构保存 → 重构 → 测试 → 如果失败：Rewind
A/B 测试保存 → 设计 A → Rewind → 设计 B → 比较
错误恢复发现问题 → Rewind 到最后一个正常状态
注意：Checkpoints 很适合会话级回退，但它不是版本控制系统。对于长期保存、可审计、可共享的改动，仍然应该使用 git。

配置

{
  "autoCheckpoint": true   # 是否自动创建 checkpoint（默认 true）
}

何时该 Rewind

  • 当前方案开始变复杂，而且还没确定方向
  • 测试刚失败，问题可能就是最近一两步引入的
  • 想比较两种实现方式
  • 想保留一个"干净起点"继续探索

Planning Mode（规划模式）

两阶段流程：先规划，再实现。

  1. 规划阶段：Claude 分析任务并生成详细实现计划
  2. 实现阶段：在你批准后，Claude 执行计划

启动方式

# Slash command

    "defaultMode": "plan"
  }
}

# 规划专用模型（Opus 规划，Sonnet 执行）

什么时候使用

✅ 适合：复杂的多文件重构、新功能开发、架构调整、数据库迁移、大型 API 重设计
❌ 不建议：简单 bug 修复、格式化修改、单文件编辑、快速查询

计划修改

User: 修改计划 - 先跳过队列，后面再加
Claude: 已更新计划：[展示删除队列后的计划]
User: 看起来不错，继续
Claude: [按修改后的计划开始实现]

Extended Thinking（扩展思考）

让 Claude 在给出解决方案前花更多时间进行复杂推理。

启用方式

  • 快捷键：Option + T（macOS）/ Alt + T（Windows/Linux）
  • 自动启用：对所有模型默认开启（Opus 4.6、Sonnet 4.6、Haiku 4.5）

Effort 级别（Opus 4.6）

  • low（○）- 低推理强度
  • medium（◐）- 中等
  • high（●）- 高
  • max - 最高（仅 Opus 4.6）
# 通过 CLI 设置

# 通过 slash command
/effort max

# 通过环境变量

{
  "thinking": {
    "enabled": true,
    "effort": "high"
  }
